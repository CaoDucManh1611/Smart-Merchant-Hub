# Isolate offline RAG evaluation from live recommendation learning

Date: 2026-11-03

## Two-agent review and live-data audit

- The main agent inspected recommendation logging and the Sol reviewer
  independently checked the persisted tenant data and code paths.
- Current aggregate: 53 recommendation requests, 50 with served items and 151
  listed items; 134 linked interaction rows, all `impression`; 0 clicks, carts,
  purchases, skips, refunds, or recommendation feedback records.
- Shop 4 has 41 served requests / 123 item impressions; shop 7 has 3 / 11.
- Shop 1 has seven historical request rows with 17 listed items, but all have
  `customer_id=NULL`, `conversation_id=0`, and no outbound bot message carrying
  recommendation metadata. They were generated by the offline evaluation
  route; they are not 17 missing customer impressions. The existing trainer
  already ignores them because they have no eligible customer.
- No conversion or ranking lift can be claimed from this data; outcomes have
  not yet been observed.

## Changes

- `prepare_rag_snapshot_eval.py` now marks deterministic serving calls as
  offline evaluation and attaches a run key to the session context.
- `_recommendation_reply()` disables live experiment selection for marked
  evaluations and calls recommendation serving without persistence.
- `serve_recommendations()` and `record_catalog_match_recommendation()` now
  support `persist=False`; in that mode they do not insert requests, commit,
  refresh, or record impressions. The default remains persistent for live API
  and chatbot traffic.
- A second Sol review found that consented offline calls could still lock and
  flush the personalization profile and could still create a bandit decision
  through an explicitly supplied experiment. Offline profile refresh now uses
  an in-memory profile object, and the service clears experiment selection
  before strategy selection when persistence is disabled.
- A final local review found that retrieval queries run before the recommendation
  service and could autoflush pre-existing session changes. Offline evaluation
  now requires a clean session at the deterministic-route boundary and checks
  again before the first retrieval/catalog query. If an offline recommendation
  reaches a dirty session, it skips that recommendation instead of flushing or
  rolling back caller-owned work.
- The reranker trainer rejects requests explicitly marked as offline evaluation,
  offline test, or synthetic traffic as a second safety barrier.
- The seven historical shop 1 rows were left intact; they are not deleted or
  relabeled in place.
- A second independent agent performed a final read-only review of the latest
  changes and found no blocker. It confirmed the pre-retrieval guard closes the
  identified autoflush path. Remaining limits: already-flushed writes cannot
  be detected, and old untagged offline rows cannot be classified by the new
  trainer filter.

## Verification and limits

- Python syntax compilation passed for the four changed Python files after the
  read-only session guards were added; `git diff --check` passed (only Git's
  normal LF/CRLF conversion warnings were emitted).
- Backend and worker were restarted to load the mounted code; both reported
  healthy afterward. Database, Redis, and frontend also remained healthy.
- No tests or training run were performed in this pass.
- This prevents evaluation traffic from polluting future live learning; it does
  not create the missing customer outcome labels. The next data-quality check
  should use a real chat recommendation followed by a tracked click or completed
  order and verify it links to the exact displayed request and product.
